How would we evaluate the performance of the agents on each ticket, and why?

I evaluate performance based on transparency and being able to follow the workflow of the agents, and the agents' ability to close out a task without requiring too many tokens. I'd also assess them on accuracy, since miscalculating cash would be problematic.

I think they did a decent job. I'd give Ticket 101 a B-, Ticket 102 an A, and Ticket 103 a B+. Ticket 101 was accurate, but it took 5 runs and three of my notes. One run spent 76,477 tokens and prepared nothing. Ticket 102 earned an A because it was pretty straightforward, moving from Facilities to Accounting, and Ticket 103 a B+ because it was a pain to sort out.

Three new problems this team could solve with the tools we built

A few examples of problems my agents could solve: a simple Yale Cap order, a Crest Mug restock, and a fake rent notice. For the Yale Cap order, check_stock would confirm the 40 Yale Caps and Customer Service could use save_customer_draft. For the Crest Mug restock, check_stock would show 0 on hand, Inventory would choose Elm City Gifts with list_vendors and confirm it can ship with get_open_invoices, and Accounting would use prepare_purchase_order for a person to approve. For a fake rent notice, Facilities would compare it with get_lease and flag a wrong sender or amount for a person, and no payment would be prepared from the notice.

Three new problems this team could not solve with the tools we built

My team would not be able to:

  1. Record the $417.60 hoodie sale
  2. Receive the tees when they arrive
  3. Plan for the $2,248 October rent gap

In order to address these problems, we would need to build out additional agents and tools as follows:

  1. A new sales agent with tools such as record_sale to capture the hoodies at $52.20 and inform the customer that there aren't any additional ones. This agent would also need a record_payment_received tool. We would need to add a new orders table and updates to the inventory and cash_accounts tables.
  2. A receiving agent with tools such as get_open_purchase_orders, to know what's coming, and record_delivery, to add what has arrived, built into inventory_receiving. We would need a deliveries table plus an update to inventory.
  3. An agent for finance planning with tools such as forecast_cash, to compare cash on hand with sales and expenses, and prepare_funding_request, for a human to evaluate. We would also need to update the database to include sales_history and funding_requests tables.
